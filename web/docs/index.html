Email Indexing for alfred_

A design for understanding the work inside an inbox.

PostgreSQL · 35 tables1 LLM call on the write pathread path: pure SQL with citationsstatus: draft

01Approach

The question behind the questions

The six questions alfred_ must answer look like search problems. They are not.

QuestionWhat it actually requires
What is waiting on me?A state that has persisted
What am I waiting on?The same state, ownership inverted
What changed?A comparison between two points in time
What am I forgetting?The absence of an expected event
What needs attention?A ranking over open state
What's slipping?Open state plus unusual silence
design stance

Every one of these is temporal or relational. None is semantic. The standard chunk-embed-retrieve pipeline is stateless on every query — it has no memory of what it concluded yesterday, so it has nothing to compare against. Embedding similarity has no concept of before, still, or no longer. Asked "what changed," such a system retrieves text that mentions change and confidently invents a change that never happened. So this design does not build a search engine over email. It builds a ledger of claims over time, and the six questions become ordinary indexed queries.

The architectural commitment

The LLM proposes. A deterministic layer disposes.

The model looks at one email and emits structured claims with supporting quotes. It does not decide current state, does not update records, does not delete anything. A plain, testable, non-AI reducer folds those claims into answers.

Consequences of this split: every stage after extraction is deterministic and unit-testable · "what changed" is a range scan, not a generation task · every answer carries a citation by construction, not by prompting · extraction can be re-run with a better prompt without corrupting history.

What this borrows, and what it can't

A useful reference point is Sybill, which does structured extraction from sales email into CRM fields. Their design works because everything anchors to a CRM object — an email attaches to a Deal, which belongs to an Account, which has known Contacts. That single fact hands them an ontology, entity resolution, and a retrieval scope. alfred_ has none of that. There is no Deal record, no externally-defined schema for "things I owe people," and no contact database resolving which humans and threads belong to the same matter. The anchor has to be manufactured. That is the central design problem here, and Section 03 is the answer to it.

02Design principles

P1

Raw observation is permanent; interpretation is revisable.

We keep the original address even after resolving it to a person, the surface form of a date even after normalising it, and the rejected extraction even after rejecting it. Anything derived can be recomputed. Anything observed cannot.

P2

Append-only where history is the product.

Monday says the deadline is Aug 15. Wednesday says Aug 20. If we stored one row and updated it, "what changed" would be unanswerable. We store both claims and compute the current value on top. Append-only storage is not hygiene here; it is the feature.

P3

One source of truth per fact.

Ownership is stored. "Waiting on me" is derived from it. Storing both means two writers for one fact, and they will eventually disagree — after which no query knows which to trust.

P4

Complexity belongs on the write path.

The quality gate runs once per email at ingest, not on every read. This is what lets the reducer stay a simple, correct one-liner.

P5

Silent failure is the enemy.

In this system a crash is not the dangerous failure. A missing obligation is. The user sees a shorter list and has no way to know something is absent. Every stage therefore records what it did, what it rejected, and why.

P6

Role changes ranking, never schema.

A founder tracks funding; a VP Finance tracks vendor spend; a Head of HR tracks offers. Underneath, all three are: someone owes someone something by some date. Topic differs, structure does not. If role drove schema, every new customer segment would be a migration, and a founder who is also the finance lead would break the model.

04Dataflows

4.1One email, end to end

design stance · automation is not discarded

Automated, organizational, and non-human messages are never thrown away. They take the index-only lane: raw storage and deterministic signals over full history, no model calls. That lane is what makes "how much of my inbox is automated," volume trends, and every behavioral aggregate answerable — while keeping extraction cost proportional to genuinely human mail (~⅓ of volume).

4.2What the extractor sees

The extractor receives the novel content of the current message plus the novel content of the previous 3–5 messages in the thread, token-capped, with the thread root always included.

Why prior messages: "Sounds good, I'll do it tomorrow" is meaningless alone. Do what?

design stance · extraction stays blind on purpose

Why NOT the current work-item state: this is a deliberate refusal. If the model sees what we already believe, it anchors on it and confirms it. Claims stop being independent evidence and become a chain of self-agreement — which is exactly what destroys change detection. The model reads "deadline: Friday," sees ambiguous new text, and re-emits Friday. Supersession is detected downstream, where it is deterministic.

Why not semantically similar emails from elsewhere: pulling a similar message from an unrelated deal invites the model to extract a deadline that is not in the source document. It also breaks the quote check, since the quote will not be found in this body.

4.3Changing information & the ordering rule

Nothing was overwritten in the ledger. The change is a first-class record with a citation, available instantly to "what changed?"

The ordering rule that prevents silent corruption. Current value is "most recent claim wins" — but most recent by which clock? Operate the fold yourself:

the reducer's view — current value per (thread, attribute)

CREATE VIEW v_current_thread_facts AS
SELECT DISTINCT ON (e.user_id, e.thread_id, e.attribute)
       e.user_id, e.thread_id, e.attribute, e.value, e.confidence,
       e.id AS source_evidence_id, e.extractor_version
FROM evidence e
JOIN emails m ON m.id = e.source_email_id
WHERE e.invalidated_at IS NULL
ORDER BY e.user_id, e.thread_id, e.attribute,
         m.provider_ts DESC, e.observed_at DESC;   -- provider_ts first. Always.

4.4Historical context and backfill

A new user may have five years of email. We do not extract over all of it. Retention and extraction depth are separate knobs:

DepthCoverageCostEnables
Raw storageAll historyStorage onlyRebuild anything, later
Deterministic signalsAll historyCPU onlyHistorical aggregates
LLM extractionRecent windowModel callsThe six questions

Collapsing these is the common mistake. If we only processed 30 days, a month-over-month question would not be expensive — it would be unanswerable, and the assistant would confabulate a trend from four data points.

Steady stateBackfill
DirectionForward in timeNewest-first
Extraction scopeAll non-automatedRecent window only
Signals scopePer emailFull history
PriorityHighRate-limited, never starves live traffic
Reducer input orderChronologicalOut of order — safe, because the fold orders by provider_ts

Backfill checkpoints its cursor. Five years of mail will fail partway through something; resuming versus restarting is the difference between a hiccup and a disaster.

design stance · closing is more dangerous than opening

A falsely-opened item is visible noise the user can dismiss in one tap. A falsely-closed item vanishes and the user never learns it existed. So completion requires higher confidence than creation, and marginal cases surface as "looks done — confirm?"

05Jobs

What runs continuously to keep alfred_'s understanding of an inbox accurate — split by trigger, because the distinction is what makes proactive assistance possible.

Event-driven"Something happened"new email arrived
Scheduled"Time made it matter"deadline near, thread quiet
Maintenance"The system watching itself"sync alive, failures visible

Only the second category can surface things the user never asked about. Nothing arrived — a deadline simply got closer, or a conversation went silent for longer than that thread's normal rhythm. That is only possible because state is materialised on write. A system that computes everything at query time has nothing to scan when no query comes.

Scheduled — time passed and made something matter

JobCadenceDetects
Deadline scanHourlyDue soon, overdue
Staleness scanDailyOpen work gone quiet
Waiting scanDailyUser blocked, counterparty silent
Commitment scanDailyPromises with no sign of delivery
Pending sweeperDailyAmbiguous claims at TTL
Attention rebuildDailyConverges the candidate set
DigestDaily, per timezoneTomorrow's precomputed answer

Staleness is measured against the thread's own rhythm, not a fixed number of days. A thread that normally replies hourly and has been silent two days is stale; one that replies weekly is not. A global threshold would flag half the inbox. threads.median_reply_gap_sec is the baseline.

Maintenance — the system watching itself

JobCadenceWhy
Subscription renewal6hGmail watch expires ~7d, Graph ~3d
Reconciliation poll6hPush delivery is lossy and unordered
Retry / dead-letter15 minA failed stage is a missing obligation
Consistency checksDailyOrphans, quarantine spikes, stale accounts
the most important job in the system

If subscription renewal dies, sync stops. No error, no exception — every answer just goes quietly stale while the system appears healthy. It runs far more often than strictly necessary precisely because the failure is invisible.

Six rules I would defend

  1. The cursor advances only after the batch commits. Advance it first and a crash loses that window permanently — provider history cursors expire and the range cannot be re-read.
  2. Extraction is a queue consumer, not a cron. A backfill burst of 400 emails must not become 400 simultaneous model calls. Concurrency is capped independently of inbound volume, so a burst degrades latency rather than breaking rate limits.
  3. The reducer folds by emails.provider_ts, not evidence.observed_at. Backfill runs newest-first, so an old email processed today has the newest observed_at. The hazard exists only during backfill, which is exactly why it survives testing and breaks in production.
  4. The change row is written before the projection, in one transaction. Reverse them and a crash between the two loses the prior value permanently — "what changed" gets a hole nobody can see.
  5. is_automated is detected from headers, never by a model. It gates whether extraction runs at all, removing roughly two thirds of volume before any model call. It sits on the cost path for every message, so it must be deterministic.
  6. Closing a work item requires higher confidence than opening one. A falsely-opened item is visible noise; a falsely-closed item vanishes and the user never learns it existed.

The three numbers that matter

These failures raise no exceptions and degrade the product invisibly.

SignalMeans
Subscriptions expiring within 24hSync about to die silently
Quarantine rate by reasonA spike in quote_not_found means the model started fabricating
created_new vs matched_existing ratioSudden shift means work items are duplicating or disappearing

Failure and recovery

Every stage is independently re-runnable, because nothing above the raw layer is a source of truth. No recovery path requires re-fetching from the provider — deliberate; history cursors expire.

Failed stageRecovery
NormalizeRe-run from raw in object storage
Signals, clusteringRe-run from stored headers and text
ExtractionRe-run from body_text_novel
ReconcileReplay evidence in provider_ts order
AttentionRegenerate from work_items

06Answering the six questions

All six are SQL. No embeddings, no router, no text-to-SQL generation.

what is waiting on me?

SELECT w.*, p.canonical_name AS requester
FROM work_items w
LEFT JOIN people p ON p.id = w.requester_person_id
WHERE w.user_id = $1
  AND w.status = 'OPEN'
  AND w.owner_is_self
  AND NOT EXISTS (
      SELECT 1 FROM attention_suppressions s
      WHERE s.work_item_id = w.id
        AND (s.suppressed_until IS NULL OR s.suppressed_until > now())
  )
ORDER BY w.due_at NULLS LAST, w.last_activity_at;

What am I waiting on someone else for? The same query with owner_is_self = FALSE, ranked by wait duration and counterparty importance. One boolean apart — which is exactly why ownership had to be modelled properly rather than inferred from status strings.

what changed?

SELECT c.field, c.prior_value, c.new_value, c.detected_at,
       w.title, e.evidence_quote, m.subject
FROM work_item_changes c
JOIN work_items w ON w.id = c.work_item_id
JOIN evidence   e ON e.id = c.new_evidence_id
JOIN emails     m ON m.id = c.triggering_email_id
WHERE c.user_id = $1 AND c.detected_at >= $2
ORDER BY c.detected_at DESC;

Old value, new value, when, why, and the citation — all in one indexed scan. The model's only remaining job on that question is phrasing the sentence.

Attention, forgetting, slipping — one pool, three filters

Slippingstale, repeated_followup"This has gone quiet"

Cross-surface suppression ensures one item appears under one framing per digest.

the honest limitation on "what am I forgetting"

Most commitments are fulfilled somewhere other than email — a call, a Slack message, a shared doc. So "a commitment with no completion evidence in email" also describes the majority of fulfilled commitments. This is a base-rate problem, not a prompt problem. No amount of prompt tuning fixes it; only narrowing the candidate definition does: surface only where someone visibly waited (a follow-up was sent, or the thread shows an unanswered ask), and the promised time has clearly passed.

Beyond the six — what the primitives already pay for

The six questions define the shape of the schema, but the schema is broader than the six because the primitives are general: an obligation with an owner, a direction, a due date, and a citation. Once you have that plus a change log, most inbox questions are a GROUP BY away.

Free today

Pure SQL over the scoped schema. No new tables.

Ownership & load
  • What's overdue, and by how long
  • Due today / this week / this month
  • Who is blocking me most often — and who am I blocking
  • What I committed to vs what I was asked for (speech_act split by owner)
  • Open work carried, trending over time
Behavioral — from signals over full history
  • Who I reply to fastest, and slowest
  • Who am I ignoring — inbound with no outbound reply
  • Needed vs merely informed (To vs Cc per sender)
  • Automated vs human share; volume trends
Change history
  • How often deadlines slip, and whose slip most
  • What I missed while away — a window query, not a digest
  • Which threads churn the most
Relationship
  • First contact, cadence, warming or cooling
Provenance — what most assistants structurally cannot do: why do you think I owe this (the actual sentence) · what was this before it changed · how confident, which extractor version · everything concluded from this one email. It falls out of append-only storage for free.

One small addition away

No model work. Days, not weeks.

  • Spend and amounts — money_mentions is one JSONB column and one regex pass. Unlocks month-over-month spend, vendor totals, invoice tracking over all history. Cheapest high-value addition on the list.
  • Company-level views — "what's open with Acme" needs organizations + organization_domains back. Two tables, domain matching, no model.
  • Meeting-adjacent obligations — anything derivable from date_mentions that isn't yet a work item.

Needs deferred work

Structural additions, listed in §10.

  • Anything semantic — "what did we discuss with Acme about pricing" needs embeddings and a router
  • Topic-level questions — "what are my active workstreams" needs segment topic labels
  • Calendar-linked questions — separate object, different mutation rules
  • Free-form anything — no text-to-SQL in scope

The honest boundary: everything above is structural — who, when, whose, how long, what changed. Nothing here answers a question about content. That's the line semantic search sits on, and it's the right first thing to add after this.

the asymmetry

Throughout, false positives are preferred to false negatives, because a false positive is visible and dismissible while a false negative is invisible. This drives the higher close threshold, the promote-as-unconfirmed policy, and the bias toward over-segmenting when segmentation arrives.

08Evaluation

The system is a chain — clustering → person resolution → extraction → matching → ranking. Errors multiply: five stages at 90% each is roughly 59% correct end to end. Without per-stage measurement, tuning goes to whichever stage happens to be under the light.

ExtractionP/R per attributeHand-labelled + quarantine rate

Free labelled data. work_item_changes records prior value, new value, causing email, and timestamp. That is a ready-made test set for extraction and matching without anyone hand-labelling anything.

proposed first experiment

Run the same corpus with and without the verbatim quote check and report the fabrication rate. It is cheap, and it directly validates the most load-bearing decision in the design.

09Scale and cost

Working assumption for a heavy user: 100–200 emails/day, roughly a third genuinely human.

~50
extractions/day/user, steady state
~1,500
extractions/user for a 30-day backfill, one time
0
model calls on 5-year history — raw + signals only

Levers, in order of effect:

  1. Automated filtering — removes ~two thirds of volume before any model runs; detected from headers (List-Unsubscribe, Precedence: bulk, Auto-Submitted, no-reply patterns), never by model judgment, because it sits on the cost path for every message.
  2. Novel-content-only extraction — cuts tokens substantially on long threads.
  3. Recent-window extraction — bounds backfill regardless of history depth.
  4. Deterministic signals over full history — historical aggregates never touch a model.
design stance

Number-shaped questions should never touch an LLM. Models are unreliable at arithmetic over long context and the data is already in SQL. Deterministic aggregation is both cheaper and more correct. Concurrency is bounded by the extraction queue, not by inbound volume, so a backfill burst degrades latency rather than breaking rate limits.

10Scope and deferred work

Scoped to exactly what the six questions require: 35 tables (34 scoped + work_item_threads added in v0.4), no vector store, no query router, no text-to-SQL. Extraction is the only LLM on the write path; the read path is entirely deterministic SQL with citations. Deferred items are listed with reasoning rather than omitted silently.

topic drift within a thread — the largest known gap

The current design assumes one thread is about one thing. In reality a thread that begins as "Q3 budget review" can drift into "office lease renewal." Both produce a due_date claim on the same thread, and latest-wins overwrites one — producing a wrong answer with a real citation attached, which is the worst failure class in the system. The fix is to segment threads and key state on the segment. Boundaries are mostly detectable without a model: a gap unusually long relative to that thread's own cadence · participants joining or leaving · the subject stem changing · semantic distance between consecutive messages against the thread's own distribution · a reply pointing several hops back. An LLM breaks ties only when signals disagree. Boundaries should be soft for retrieval but hard for state — the extractor may read across a boundary for context, but the fold must not cross one.
