01Approach

The question behind the questions

The six questions alfred_ must answer look like search problems. They are not.

QuestionWhat it actually requires
What is waiting on me?A state that has persisted
What am I waiting on?The same state, ownership inverted
What changed?A comparison between two points in time
What am I forgetting?The absence of an expected event
What needs attention?A ranking over open state
What's slipping?Open state plus unusual silence
A ledger, not a search index

All six questions are temporal or relational; none is semantic. A chunk-embed-retrieve pipeline is stateless per query — nothing to compare against, so "what changed" gets invented. We store a ledger of claims over time instead; the six questions become indexed queries.

The architectural commitment

The LLM proposes. A deterministic layer disposes.

  • The model reads one email and emits structured claims with quotes. It never decides current state, never updates, never deletes.
  • A plain, testable reducer folds claims into answers — every stage after extraction is deterministic and unit-testable.
  • "What changed" is a range scan, not a generation task.
  • Every answer carries a citation by construction, not by prompting.
  • Extraction can be re-run with a better prompt without corrupting history.

02Design principles

P1

Raw observation is permanent; interpretation is revisable.

Keep the original address, the date's surface form, the rejected extraction. Derived data can be recomputed; observed data cannot.

P2

Append-only where history is the product.

Store every claim; compute current value on top. Updating in place makes "what changed" unanswerable.

P3

One source of truth per fact.

Ownership is stored; "waiting on me" is derived. Two writers for one fact eventually disagree.

P4

Complexity belongs on the write path.

The quality gate runs once at ingest, so the reducer stays a simple, correct one-liner.

P5

Silent failure is the enemy.

A missing obligation is worse than a crash. Every stage records what it did, what it rejected, and why.

P6

Role changes ranking, never schema.

Founder, VP Finance, Head of HR — all reduce to: someone owes someone something by some date. Role tunes ranking; the schema never migrates.

04Dataflows

4.1One email, end to end

The gate is noise, not automation

Automated is a mechanism; noise is a judgment. Only noise skips the model — spam, newsletters, adverts, promotions, list archives: bulk mail with nothing to track.

  • Machine-sent is not disqualifying. An application moving to interview, a receipt, a ticket update, a delivery confirmation — all arrive from no-reply@, all close or advance real work items. Gating on is_automated would silently drop every one.
  • So the flag is keyed on bulk markers (List-Unsubscribe + Precedence: bulk + ESP return-path + provider spam/promotions labels), not on Auto-Submitted or a no-reply local part alone.
  • Noise is never thrown away — stored and signalled over full history, so volume trends and "how much of my inbox is marketing" stay answerable. It just never reaches the model.

4.2What the extractor sees

  • In: novel text of the current message + the previous 3–5 novel texts, token-capped, thread root always included.
  • Why prior messages: "Sounds good, I'll do it tomorrow" is meaningless alone.
  • Out — similar mail from other threads: invites extracting a deadline that isn't in the source, and breaks the quote check.
Extraction stays blind on purpose

The model never sees current work-item state. If it did, it would anchor and re-confirm — claims become self-agreement, and change detection dies. Supersession is detected downstream, where it is deterministic.

4.4Historical context and backfill

A new user may have five years of email. We do not extract over all of it. Retention and extraction depth are separate knobs:

DepthCoverageCostEnables
Raw storageAll historyStorage onlyRebuild anything, later
Deterministic signalsAll historyCPU onlyHistorical aggregates
LLM extractionRecent windowModel callsThe six questions

Collapse these and a month-over-month question is not expensive — it is unanswerable.

Steady stateBackfill
DirectionForward in timeNewest-first
Extraction scopeAll non-noiseRecent window only
Signals scopePer emailFull history
PriorityHighRate-limited, never starves live traffic
Reducer input orderChronologicalOut of order — safe, because the fold orders by provider_ts

Backfill checkpoints its cursor: five years of mail will fail partway through something, and resuming vs restarting is the difference between a hiccup and a disaster.

Closing is more dangerous than opening

A falsely-opened item is visible noise the user can dismiss in one tap. A falsely-closed item vanishes and the user never learns it existed. So completion requires higher confidence than creation, and marginal cases surface as "looks done — confirm?"

05Jobs

What runs continuously to keep alfred_'s understanding of an inbox accurate — split by trigger, because the distinction is what makes proactive assistance possible.

Event-driven"Something happened"new email arrived
Scheduled"Time made it matter"deadline near, thread quiet
Maintenance"The system watching itself"sync alive, failures visible

Only the scheduled category can surface things the user never asked about — possible only because state is materialised on write. A system that computes everything at query time has nothing to scan when no query comes.

Scheduled — time passed and made something matter

JobCadenceDetects
Deadline scanHourlyDue soon, overdue
Staleness scanDailyOpen work gone quiet
Waiting scanDailyUser blocked, counterparty silent
Commitment scanDailyPromises with no sign of delivery
Pending sweeperDailyAmbiguous claims at TTL
Attention rebuildDailyConverges the candidate set
DigestDaily, per timezoneTomorrow's precomputed answer

Staleness is measured against the thread's own rhythm (threads.median_reply_gap_sec), not a fixed number of days — a global threshold would flag half the inbox.

Maintenance — the system watching itself

JobCadenceWhy
Subscription renewal6hGmail watch expires ~7d, Graph ~3d
Reconciliation poll6hPush delivery is lossy and unordered
Retry / dead-letter15 minA failed stage is a missing obligation
Consistency checksDailyOrphans, quarantine spikes, stale accounts
The most important job in the system

If subscription renewal dies, sync stops. No error, no exception — every answer just goes quietly stale while the system appears healthy. It runs far more often than strictly necessary precisely because the failure is invisible.

Six rules I would defend

  1. The cursor advances only after the batch commits. Advance it first and a crash loses that window permanently — provider history cursors expire and the range cannot be re-read.
  2. Extraction is a queue consumer, not a cron. A backfill burst of 400 emails must not become 400 simultaneous model calls. Concurrency is capped independently of inbound volume, so a burst degrades latency rather than breaking rate limits.
  3. The reducer folds by emails.provider_ts, not evidence.observed_at. Backfill runs newest-first, so an old email processed today has the newest observed_at. The hazard exists only during backfill, which is exactly why it survives testing and breaks in production.
  4. The change row is written before the projection, in one transaction. Reverse them and a crash between the two loses the prior value permanently — "what changed" gets a hole nobody can see.
  5. The noise gate is detected from headers, never by a model. It decides whether extraction runs at all, removing roughly two thirds of volume before any model call, so it must be deterministic. It keys on bulk markers — not on machine-sent — so transactional automated mail still reaches the model.
  6. Closing a work item requires higher confidence than opening one. A falsely-opened item is visible noise; a falsely-closed item vanishes and the user never learns it existed.

The three numbers that matter

These failures raise no exceptions and degrade the product invisibly.

SignalMeans
Subscriptions expiring within 24hSync about to die silently
Quarantine rate by reasonA spike in quote_not_found means the model started fabricating
created_new vs matched_existing ratioSudden shift means work items are duplicating or disappearing

Failure and recovery

Every stage is independently re-runnable, because nothing above the raw layer is a source of truth. No recovery path requires re-fetching from the provider — deliberate; history cursors expire.

Failed stageRecovery
NormalizeRe-run from raw in object storage
Signals, clusteringRe-run from stored headers and text
ExtractionRe-run from body_text_novel
ReconcileReplay evidence in provider_ts order
AttentionRegenerate from work_items

06Answering the six questions

All six are SQL. No embeddings, no router, no text-to-SQL. Full statements in §11 SQL reference.

  • Waiting on me: work_items WHERE OPEN AND owner_is_self, minus suppressions, ordered by due date.
  • Waiting on others: the same query, one boolean flipped — which is why ownership is modelled, not inferred from status strings.
  • What changed: a range scan on work_item_changes since $t — old value, new value, when, why, and the citation in one indexed scan. The model's only remaining job is phrasing the sentence.

Attention, forgetting, slipping — one pool, three filters

Surfacereason valuesFraming
Needs attentiondue_soon, overdue, unanswered_request"These need you today"
Forgettingunfulfilled_commitment"You said you'd…"
Slippingstale, repeated_followup"This has gone quiet"

Cross-surface suppression ensures one item appears under one framing per digest.

The honest limitation on “what am I forgetting”

Most commitments are fulfilled off-email (call, Slack, doc), so "no completion evidence in email" also describes most fulfilled commitments. A base-rate problem, not a prompt problem. The only fix is a narrower candidate: someone visibly waited, and the promised time clearly passed.

Beyond the six — what the primitives already pay for

The primitives are general — an obligation with an owner, a direction, a due date, a citation, plus a change log. Most inbox questions are a GROUP BY away.

Free today

Pure SQL over the scoped schema. No new tables.

Ownership & load
  • What's overdue, and by how long
  • Due today / this week / this month
  • Who is blocking me most often — and who am I blocking
  • What I committed to vs what I was asked for (speech_act split by owner)
  • Open work carried, trending over time
Behavioral — from signals over full history
  • Who I reply to fastest, and slowest
  • Who am I ignoring — inbound with no outbound reply
  • Needed vs merely informed (To vs Cc per sender)
  • Automated vs human share; volume trends
Change history
  • How often deadlines slip, and whose slip most
  • What I missed while away — a window query, not a digest
  • Which threads churn the most
Relationship
  • First contact, cadence, warming or cooling
Provenance — what most assistants structurally cannot do: why do you think I owe this (the actual sentence) · what was this before it changed · how confident, which extractor version · everything concluded from this one email. It falls out of append-only storage for free.

One small addition away

No model work. Days, not weeks.

  • Spend and amounts — money_mentions is one JSONB column and one regex pass. Unlocks month-over-month spend, vendor totals, invoice tracking over all history. Cheapest high-value addition on the list.
  • Company-level views — "what's open with Acme" needs organizations + organization_domains back. Two tables, domain matching, no model.
  • Meeting-adjacent obligations — anything derivable from date_mentions that isn't yet a work item.

Needs deferred work

Structural additions, listed in §10.

  • Anything semantic — "what did we discuss with Acme about pricing" needs embeddings and a router
  • Topic-level questions — "what are my active workstreams" needs segment topic labels
  • Calendar-linked questions — separate object, different mutation rules
  • Free-form anything — no text-to-SQL in scope

The boundary: everything above is structural — who, when, whose, how long, what changed. Nothing answers a question about content. That is where semantic search sits, and it is the right first addition after this.

The asymmetry

False positives beat false negatives: a false positive is visible and dismissible; a false negative is invisible. This drives the higher close threshold, promote-as-unconfirmed, and the bias toward over-segmenting.

08Evaluation

The system is a chain — clustering → person resolution → extraction → matching → ranking. Errors multiply: five stages at 90% ≈ 59% end to end. Without per-stage measurement, tuning goes to whichever stage is under the light.

ComponentMetricLabel source
Thread clusteringPairwise P/RHand-labelled sample
Person resolutionCluster purityHand-labelled sample
ExtractionP/R per attributeHand-labelled + quarantine rate
OwnershipAccuracyHand-labelled
Work item matchingP/R on duplicates and mergesUser corrections
RankingNDCG @ 5feedback_events
End to endAnswer accuracy on the sixCurated question set

Free labelled data. work_item_changes records prior value, new value, causing email, and timestamp. That is a ready-made test set for extraction and matching without anyone hand-labelling anything.

Proposed first experiment

Run the same corpus with and without the verbatim quote check and report the fabrication rate. It is cheap, and it directly validates the most load-bearing decision in the design.

09Scale and cost

Working assumption for a heavy user: 100–200 emails/day, roughly a third genuinely human.

~50
extractions/day/user, steady state
~1,500
extractions/user for a 30-day backfill, one time
0
model calls on 5-year history — raw + signals only

Levers, in order of effect:

  1. Noise filtering — removes ~two thirds of volume before any model runs; detected from headers (List-Unsubscribe, Precedence: bulk, ESP return-path, provider spam/promotions labels), never by model judgment, because it sits on the cost path for every message. Auto-Submitted and no-reply alone do not qualify — transactional machine mail still carries trackable state.
  2. Novel-content-only extraction — cuts tokens substantially on long threads.
  3. Recent-window extraction — bounds backfill regardless of history depth.
  4. Deterministic signals over full history — historical aggregates never touch a model.
Numbers never touch the model

Number-shaped questions never touch an LLM. Models are unreliable at arithmetic; the data is already in SQL. Deterministic aggregation is cheaper and more correct.

10Scope and deferred work

35 tables (34 scoped + work_item_threads, v0.4). No vector store, no query router, no text-to-SQL. Deferred items are listed with reasoning, not omitted silently.

Topic drift within a thread — the largest known gap

The design assumes one thread is about one thing. A thread that drifts ("Q3 budget" → "office lease") folds two due-dates onto one key, and latest-wins overwrites one — a wrong answer with a real citation attached, the worst failure class in the system. Fix: segment threads, key state on the segment.

  • Boundary signals, no model needed: unusual gap vs the thread's own cadence · participants join/leave · subject stem changes · semantic distance jump · reply pointing several hops back.
  • An LLM breaks ties only when signals disagree.
  • Boundaries: soft for retrieval, hard for state — the extractor may read across; the fold must not.

The six-question queriesread path 
-- What is waiting on me?
SELECT w.*, p.canonical_name AS requester
FROM work_items w
LEFT JOIN people p ON p.id = w.requester_person_id
WHERE w.user_id = $1
  AND w.status = 'OPEN'
  AND w.owner_is_self
  AND NOT EXISTS (
      SELECT 1 FROM attention_suppressions s
      WHERE s.work_item_id = w.id
        AND (s.suppressed_until IS NULL OR s.suppressed_until > now())
  )
ORDER BY w.due_at NULLS LAST, w.last_activity_at;

-- What am I waiting on someone else for?
-- The same query with owner_is_self = FALSE.

-- What changed?
SELECT c.field, c.prior_value, c.new_value, c.detected_at,
       w.title, e.evidence_quote, m.subject
FROM work_item_changes c
JOIN work_items w ON w.id = c.work_item_id
JOIN evidence   e ON e.id = c.new_evidence_id
JOIN emails     m ON m.id = c.triggering_email_id
WHERE c.user_id = $1 AND c.detected_at >= $2
ORDER BY c.detected_at DESC;

-- Attention / forgetting / slipping: one pool, filtered by reason.
SELECT ac.*, w.title
FROM attention_candidates ac
JOIN work_items w ON w.id = ac.work_item_id
WHERE ac.user_id = $1
  AND ac.reason = ANY($2)          -- per surface
ORDER BY ac.score DESC
LIMIT 10;
